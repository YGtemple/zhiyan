Internal Architecture

个人口述表达教练，从一次报告升级为连续训练系统。

本页给团队成员对齐当前项目架构：用户画像、基线测试、口述分析、评分建模、训练任务、进步流、前后端边界和统一仓库协作。

一、系统主链路

1. 训练目标选择公开演讲、闲聊、会议表达、面试、路演等方向。
2. 用户画像记录场景、听众、痛点、自评、表达频率和训练优先级。
3. 基线测试30 到 60 秒口述测试，形成初始表达向量。
4. 口述分析规则分析器和大模型共同输出结构化诊断。
5. 训练任务每个问题绑定训练方向、练习方式和完成标准。
6. 二次口述用户按任务重讲，同一场景形成对照样本。
7. 进步流更新画像、历史趋势和下一轮训练路径。

三、前端架构

页面模块

  • Goal Setup：训练方向、场景、听众、时长、痛点选择。
  • Baseline Test：30 到 60 秒测试题、文本输入、转写结果确认。
  • Analysis Workspace：展示结构、连贯性、关键词、场景适配等诊断。
  • Training Plan：每个问题对应训练方向、练习方式、完成标准。
  • Progress Stream：按时间线展示每次口述、分数变化、下一轮目标。
  • Team Debug View：团队内部查看 JSON、评分权重、prompt 版本和模型输出。

前端状态边界

Client State ├─ activeGoalId ├─ activeSessionId ├─ draftTranscript ├─ selectedScenario ├─ pendingAnalysis └─ reportViewMode Server State ├─ UserProfile ├─ SpeechAttempt ├─ AnalysisReport ├─ TrainingAssignment └─ ProgressSnapshot

交互原则

前端不让用户面对空白 prompt，而是用目标、场景、时长和示例题引导输入。

报告原则

报告页面先给结论，再给证据摘录，最后给可执行训练任务。

团队调试

内部视图暴露 schema、模型版本、评分版本和任务映射，便于多人协作。

四、后端架构

服务模块

API Layer ├─ POST /api/profile ├─ POST /api/baseline ├─ POST /api/attempts ├─ POST /api/analyze ├─ GET /api/reports/:id └─ GET /api/progress/:profileId Domain Services ├─ ProfileService ├─ AttemptService ├─ AnalysisOrchestrator ├─ RuleScoringEngine ├─ LlmAnalysisAdapter ├─ TrainingPlanner ├─ ProgressEngine └─ SourceRegistry

分析编排

  • 先跑规则分析：字数、句长、缓冲词、重复、请求位置、结构标记。
  • 再跑大模型分析：语义连贯、听众负担、场景适配、表达目标达成度。
  • 合并为统一 JSON 报告，不让模型自由输出页面文案。
  • 训练任务只从任务库和来源注册表中匹配，不直接凭空生成。

LLM Adapter

封装模型、prompt、JSON schema 校验、重试、成本记录和模型版本。

Rule Engine

提供稳定可测的基础指标，避免所有评分都依赖大模型主观判断。

Progress Engine

比较历次表达向量，生成趋势、训练优先级和下一轮任务难度。

七、训练任务映射

问题识别

每个 issue 必须包含问题类型、证据摘录、影响说明和所属评分维度。

任务匹配

根据 issue.direction 从训练任务库匹配，而不是让模型随意给建议。

进步更新

二次口述后更新同一维度分数，记录该任务是否真的改善表达。

Issue -> Direction -> Drill -> Success Criteria -> Next Attempt Prompt -> Progress Snapshot

八、统一仓库协作架构

建议仓库结构

tedify-v2/ ├─ apps/ │ └─ web/ # 团队和用户共用 Web App ├─ packages/ │ ├─ core/ # 类型、schema、领域对象 │ ├─ analyzer/ # 规则评分与文本特征 │ ├─ llm/ # LLM adapter、prompt、JSON 校验 │ ├─ curriculum/ # 训练任务库与来源注册表 │ ├─ progress/ # 进步流和历史对比 │ └─ eval/ # 黄金样例和回归测试 ├─ docs/ │ ├─ ARCHITECTURE.md │ ├─ RUBRIC.md │ └─ API-CONTRACTS.md └─ tests/ ├─ fixtures/ └─ integration/

协作边界

  • 前端只依赖 API contract 和 schema。
  • 后端只返回结构化报告，不返回拼好的页面。
  • 评分模型版本化，报告必须记录 rubricVersion。
  • 训练任务库独立维护，可单独评审。
  • 每个代理只改自己负责的 package。
